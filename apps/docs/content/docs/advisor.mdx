The advisor is KubeHero's agentic layer. It reads the same telemetry the dashboard shows — waste recommendations, spend anomalies, burn rate, team spend — and turns it into a **briefing**: a one-line headline, a full markdown report, a spoken script you can play out loud, and a queue of **proposed actions**. Each action carries a ready-to-apply policy CRD manifest.

The division of labor is strict and worth memorizing:

> **Advisor proposes · humans arm · operator executes.**

The advisor runs as its own Deployment (Connect-RPC on `:8083`). It has no Kubernetes credentials, calls only the control plane's read RPCs, and cannot mutate anything — by construction, not by configuration.

## Brain tiers

The advisor picks one of three brains at startup based on what you've configured:

| Tier | Selected when | What you get |
|---|---|---|
| **llm** | `ANTHROPIC_API_KEY` is set | Claude narrates the briefing and drafts proposals. Any failure — API outage, timeout, malformed output — silently falls back to the rules tier. Briefings never fail because Anthropic is down. |
| **rules** | No API key | Deterministic: the same snapshot always produces the same briefing. No external API calls at all. |
| **demo** | No `CONTROL_PLANE_URL` | Built-in fixture data so the Advisor page works out of the box. Every briefing is stamped `source: "demo"` and the dashboard badges it, so it can't be mistaken for real data. |

The rules tier is not a degraded mode — it's the offline default, the fallback, and what the test suite exercises. The LLM tier adds narrative quality and cross-signal reasoning on top; it does not add any new powers.

## Enabling the LLM brain

Create a Secret holding your Anthropic API key, then point the chart at it:

```bash
kubectl -n kubehero-system create secret generic anthropic \
  --from-literal=api-key=sk-ant-...
```

```yaml
# values.yaml
advisor:
  enabled: true
  anthropic:
    existingSecret: "anthropic"   # name of the Secret above
    secretKey: "api-key"          # key inside it
```

Leave `existingSecret` empty (the default) and the advisor runs the rules brain — nothing ever leaves your cluster.

**Privacy note**: with the LLM tier enabled, the briefing input — a compact snapshot of cluster names, workload names, dollar amounts, and anomaly descriptions — is sent to Anthropic's API. If that snapshot is sensitive in your environment, stay on the rules tier.

## The guardrail contract

Every proposed action passes the same validation, no matter which brain produced it:

- **Action kinds are whitelisted.** Only `rightsize.requests`, `ceiling.arm`, `nodepool.consolidate`, and `workload.investigate` exist. Anything else is rewritten.
- **Manifests are policy CRDs or nothing.** An action's `crd_yaml` must parse as YAML and declare one of `BudgetPolicy`, `CeilingPolicy`, or `RightsizingPolicy` — the operator's three guarded CRDs (see the [CRD reference](/docs/crd-reference)).
- **Numbers are sanitized.** Dollar impacts must be finite and ≥ 0 (clamped otherwise); risk must be `low` / `medium` / `high` (defaults to `medium`).
- **Failures downgrade, never escalate.** An action that fails any check becomes a `workload.investigate` proposal with **no manifest attached** — it is never silently passed through as something applyable.
- **Status is always `proposed`.** The advisor cannot emit an "approved" or "applied" action.

Applying a proposal is a human act: you take the manifest, `kubectl apply` it (or use the dashboard), and arm it through the operator's normal `humanArm` flow. The LLM cannot skip any step of that chain.

## RPC surface

Two methods on `kubehero.v1.AdvisorService` (proto source of truth: `packages/proto/kubehero/v1/advisor.proto`):

```proto
// The full briefing: headline, markdown report, spoken script, actions.
rpc GetBriefing(GetBriefingRequest) returns (GetBriefingResponse) {}

// Just the proposed actions — the action queue without the narrative.
rpc ListAdvice(ListAdviceRequest) returns (ListAdviceResponse) {}
```

`GetBriefingRequest` takes an optional `cluster_id` (empty = fleet-wide) and a `window` (`"24h"` default, `"7d"` supported). The response's `Briefing.source` tells you which brain answered: `"llm"`, `"rules"`, or `"demo"`.

```bash
buf curl \
  --schema packages/proto \
  --protocol connect \
  --data '{"window": "24h"}' \
  http://localhost:8083/kubehero.v1.AdvisorService/GetBriefing
```

Briefings are cached in-memory for **10 minutes** per cluster + window, so dashboard reloads don't re-bill the LLM tier. The advisor also degrades on the input side: if the control plane becomes unreachable mid-flight, it serves a clearly-marked demo snapshot rather than erroring.

## Voice briefings

The dashboard's **Advisor** page renders the briefing and its proposed-action queue, and the play button speaks the briefing's `spoken_script` using the browser's built-in SpeechSynthesis API. There is no external TTS service, no audio leaves the machine, and browsers without speech support show a quiet "not supported" chip instead of a broken button.

## What the AI cannot do

An honest list, because "AI-powered" claims deserve suspicion:

- **It cannot apply anything.** No Kubernetes credentials, no `kubectl`, no write RPCs. Its output is text and manifests for *you* to apply.
- **It cannot call mutation RPCs.** Its only control-plane inputs are `ListClusters`, `ListWasteRecommendations`, `ListAnomalies`, `GetTeamSpend`, and `GetBurnRate` — all reads.
- **It cannot bypass `humanArm`.** Even a proposal you apply verbatim still sits unarmed until you arm it.
- **It cannot invent new action types.** Off-whitelist kinds and malformed manifests are downgraded to investigate-only proposals.
- **It cannot take the page down.** LLM failures fall back to rules; control-plane outages fall back to a labeled demo snapshot.
- **It can still be wrong.** Dollar impacts are estimates grounded in the snapshot, and an LLM can misjudge which action matters most. Read the rationale, review the manifest, and treat every proposal as a draft from a well-informed colleague — not an instruction.
